| D140（Z2） | 輸入 `Alloc_In!C32`＝0.2 | 是 | 能失敗；`Alloc_In!C33` 為四項相加，與舊公式等價 |

**V23、V24 是否為結構性恆等式：是，我同意建置報告。**

- **V23**（實際每用戶速度 ≥ SLO）：`Perf` 第 85 列的批次上限是從 SLO 反解出來的（`=(1000×每秒token÷SLO − 固定延遲) ÷ 每序列時間`），第 89 列的實際速度再用同一組數字代回去算，兩者代數上必相等；當 HBM 容量先限制時，採用批次更小，速度只會更高。唯一例外是批次反解結果 ≤ 0（SLO 不可達），此時該欄被排除不計。因此**任何輸入組合都無法讓它失敗**，只有公式被改壞，或分母為 0 使整個算式出錯（`IFERROR` 回 1，但這種輸入本來就會被 GOV 抓到）才會亮紅燈。
- **V24**（Cap_In 第 147 列 ＝ `L1_MImplied`）：第 147 列的分子是「訂閱營收＋席次營收＋API 營收」，其中 API 營收被定義為「總營收 − 訂閱 − 席次」的餘額，所以分子永遠等於總營收；分母「API＋消費訂閱＋商用席次 token」中，後兩者是 ChatGPT 付費 token 乘份額與（1−份額），加起來永遠等於 ChatGPT 付費 token。`L1_MImplied` 則直接是 `Cap_In!C94`＝總營收 ÷（ChatGPT＋API token）。兩邊代數上相同，**沒有任何輸入能讓它們不同**。
- 這兩條能抓到的只有「公式被改壞」，不能抓到「輸入出錯」。建議採建置報告第 10 節的選項：改標「恆等式（非驗證）」（如 V18）而不是計入驗證項目數；目前計入使驗證計數 Total 24、Pass 16 略有灌水（兩條）。這是**判斷類**，我不動。
