  - Exit codes 一節：「bash/sh: By default, fail-fast behavior is enforced using set -e for both sh and bash. When shell: bash is specified, -o pipefail is also applied to enforce early exit from pipelines that generate a non-zero exit status.」
- 本機模擬：把步驟內容（`bash <腳本> | tee -a <檔>` 加一行後續命令）分別用兩種 shell 執行。

| 情境 | 未指定 shell（`bash -e`） | `shell: bash`（`bash --noprofile --norc -eo pipefail`） |
|---|---|---|
| 腳本 `exit 1`（apt 失敗） | 結束碼 **0**，後續命令照跑 | 結束碼 **1**，後續命令不跑 |
| apt 回報成功但找不到 soffice（PATH 清空） | 結束碼 **0** | 結束碼 **1** |

  也就是說：修改前，安裝失敗被 `tee` 的結束碼 0 遮蓋，job 繼續到測試才因找不到 `soffice` 失敗（v5.25 run 207／208、v5.26 run 214 的情形）；修改後，job 會在安裝步驟本身失敗。
- 實際 CI：run 216／217 的安裝步驟都成功（例：scenarios 第 4 片 37 秒），沒有遇到失敗情境，所以「實際失敗時停在安裝步驟」只由上述文件與本機模擬驗證，CI 上尚未實際觸發。job 日誌的下載網址被本環境代理擋下（403），無法引用 runner 上 `shell:` 行的原文。

### 3.2 ci-status 重跑殘留
- 原因（以 run 214 實查）：重跑失敗 job 後，artifacts API 同一個 run 會列出兩次嘗試上傳的同名 artifact（例：`parity-results-scenarios-1` 有 15:35:50 與 15:47:38 兩筆、`-3` 也有兩筆），回應沒有嘗試編號欄；`ci_status.py` 兩筆都讀，於是把第 1 次的失敗也列進 `failures`。
- 修改：新增 `latest_per_name`，同名 artifact 只取 `created_at` 最新的一筆（同時間再比 id）。重跑只重跑失敗的 job，未重跑的 job 沿用前次的結果檔，所以「每個名稱取最新一筆」恰好是本次嘗試各 job 的結果。`overall` 判定沒有改（仍取 `needs.parity.result`）。沒有改用 `GITHUB_RUN_ATTEMPT` 篩選，因為未重跑 job 的 artifact 屬於前次嘗試，用嘗試編號篩選會漏掉。
- 驗證方式：**模擬**——新測試 `test_rerun_failures_only_from_latest_attempt` 以 run 214 實際的 artifact id 與建立時間組成清單（舊的一筆有 `soffice` 失敗、新的一筆通過），確認 `failures` 為空；反向確認最新一筆仍失敗時照列（只去重，不吞失敗）。本輪 CI 沒有重跑，所以沒有實際重跑的驗證。
