一句話：大批次低估**幾乎全部發生在服務 SLO 以外的批次範圍**。服務 SLO 下的批次很小：Hopper 每 GPU 1–9 序列，GB200 6–49 序列。因此不論 (a) 或 (b)，對 `L1_MFleet` 的影響都在 0 到 −0.05 之間。真正會讓 m 大幅下降的，是把差距當作「世代水準」（不分批次的常數倍數），那會使 m 降到約 0.17，但這和小批次的證據（MLPerf 上限、InferenceX 旁證）衝突 1.5–4 倍。

## 1. (a) 與 (b) 的區分結論

### 1.1 (a) 通訊重疊：不是主因（信心高）

1. **模型的時間結構**：每步時間＝固定延遲（權重讀取＋每層延遲 × 層數）＋ 批次 × 每序列時間。每序列時間取「算力、KV 讀取、EP 通訊」三項中最大的一項（Perf 第 83 列寫明「假設三者可重疊」；Calib J 節第 190 列相同）。也就是說，**EP 通訊和算力本來就被當作完全重疊**。只有固定延遲是直接相加的。
2. **EP 通訊項在現行 η_d 下不是最大項**：
   - Hopper 校準點：算力 1.113 ms 對 EP 0.2975 ms／序列；
   - GB200 校準點：算力 0.249 ms 對 EP 0.0146 ms；
   - 服務 Sol 欄：Hopper 算力 6.28 ms 對 EP 0.885 ms。
   所以把 EP 項縮小，數字完全不動（Q4 A1：遮 50% 與 65%，全部 0 變動）。
3. **算力項本身才是瓶頸**：Hopper 校準點目標每步 55.1 ms，但光是算力項 × 批次就有 128 × 1.113＝142 ms。即使固定延遲完全歸零，每序列算力仍要縮小 **2.59 倍**。GB200 同理，要縮小 **2.51 倍**。這個缺口只有 η_d 能補，任何通訊重疊的假設都補不了。
4. **GB200 校準點本身沒有重疊**：vLLM 10.1K 的文章把「計算與通訊重疊」列為未來工作；SGLang 在 GB200 上把 TBO 關掉，因為 NVLink 通訊快、重疊反而浪費。
5. **只有在 η_d 先提高之後，(a) 才有作用**：η_d 提高約 3.7 倍後，Hopper 的每序列時間改由 EP 通訊項決定（0.2975 ms），產出上限是目標的 0.94。這時 EP 項的精確度才重要。DeepSeek 論文的理論式（每層 120.96 µs／32 token）相當於模型 EP 通訊效率取 1.0（模型現為 0.7），此時 EP 下限為 0.208 ms，低於達標所需的 0.2705 ms，校準點就有解（所需倍數 4.11；Q4 以「EP 遮 50%」試算 B1＋A1，比值 1.00）。

### 1.2 (b) η_d 隨批次上升：方向成立，形狀不確定（信心：方向中、形狀低）

支持的證據：
- 所有大批次點的隱含整步 MFU 都是 9.0%–12.5%：DeepSeek profile 11.1%、DeepSeek 線上 9.3%、LMSYS H100 12.5%、vLLM GB200 9.0%、LMSYS GB200 11.9%。模型 η_d 是 3.6%–4.3%。
- 同一來源的掃描顯示 MFU 會隨批次上升：MLPerf GB200 3.4% → 7.0%；TensorRT-LLM H200 從 batch 1 的 0.12% 到每 rank 128 的 8.9%。
- 物理機制成立：專家矩陣運算的效率取決於每個專家分到的 token 數。字節跳動的分析例子是每專家 39 token 時，FFN 理論 MFU 只有 25%。GB300 擬合點每步只有 13–76 token；大批次點每步 128–1,339 token。

不支持「平滑隨批次上升」的證據：
1. **Hopper 驗證點對不上**。DeepSeek 線上的條件是每用戶 21 tok/s、每 GPU 約 88 序列；LMSYS 是 10 tok/s、約 278 序列。在任何平滑形狀下，模型在這兩個 SLO 下解出的批次都停在低批次（23、74 序列）。要對上這兩點，每 GPU 約 88 序列時 η_d 就必須已經是大批次水準（倍數約 3.7），而 InferenceX 與 MLPerf v5.1 顯示 48 序列以下倍數為 1。這相當於在 48 到 88 序列之間突然跳 3.7 倍。比較合理的解讀是兩種部署型態不同，而不是單純的批次效應。大批次點都是寬 EP（每 GPU 只放 2–4 個專家）、PD 分離的系統；小批次點則是單機 8 GPU 或小 EP。
2. **MLPerf 上限衝突**：只要 η_d 的形狀能對上 vLLM 10.1K，V2（MLPerf v6.0 GB200 server 4,668）就會升到 1.7–1.8 而失敗。但 MLPerf server 的 80 ms 是 p99，模型拿它當平均每步時間；TensorRT-LLM 在同一台 H200、相近的每用戶速度（11.35 對 12.5 tok/s）、沒有尾端延遲限制的條件下，吞吐是 MLPerf v5.1 的 2.6 倍（1,436 對 556）。所以「模型 ≤ MLPerf server」可能不是硬上限，這要 Project 判斷。
3. **MLPerf 同一來源內沒有 3 倍缺口**：模型與 MLPerf offline 的比值是 0.57（GB200）、0.65（GB300），interactive 是 0.49、0.70。開源大批次點則是 0.26–0.37。兩類來源在相近的大批次下相差 1.4–1.9 倍（例如 GB200：MLPerf offline 換成 decode-only 約 7,000，對 vLLM 10.1K、LMSYS 13.4K）。

### 1.3 還缺什麼證據

- **同一系統、同一軟體下的 decode 批次掃描（Hopper、寬 EP）**：例如 DeepSeek profile 在 32／64／128 序列的每步時間。已搜尋，未找到（DeepSeek、SGLang、vLLM 的批次掃描都只在圖中，文字沒有數字）。
- **MLPerf server 的平均 TPOT 與 p99 的比值**：用來判斷 V2 能不能當作上限。
- **開關 TBO／DBO 的消融與通訊占比**：SGLang 的 profile 圖沒有讀到數字，vLLM 沒有單獨消融，Perplexity 的頁面讀取被擋。

讀法：
1. **形狀**：同一來源內 MFU 隨批次上升，但從 server 到 offline 只上升 1.45–1.62 倍（第二來源：CoreWeave GB200 1.50、Google GB200 1.96）。在模型裡，從 server 到 offline，模型比值只下降 1.26–1.40 倍。所以在 MLPerf 這一類系統中，「模型低估隨批次放大」的幅度約 1.3–1.4 倍，不是 3 倍。

## 4. Q3 Hopper 在中等互動速度下的實測

- **非 SemiAnalysis：已搜尋，未找到**有寫明硬體、EP、批次與每用戶速度的 H100／H200 點（管道：WebSearch 3 組；LMSYS 96×H100 與 GB200 兩篇；vLLM 兩篇；TensorRT-LLM 最佳實務文件；dstack H200 對 MI300X 的比較，數字只在圖中；Perplexity，讀取被擋）。
- 找到的非 SemiAnalysis 相關點：
  - 螞蟻集團 H20（Analogy）：TPOT <30 ms（約 33 tok/s）、每 GPU 12 序列、MTP → 423 tok/s/GPU；TPOT <50 ms（20 tok/s）→ 675。
  - TensorRT-LLM H200 只有兩端：batch 1 時 158 tok/s/user；並行 1,024 時 11.35 tok/s/user。
- **旁證（InferenceX H200，SGLang FP8，8K／1K）**：30 tok/s/user → 1,582；50 → 1,235；75 → 932；100 → 739 tok/s/GPU。口徑沿用本工作簿擬合點的「每 GPU 總 token（輸入＋輸出）」，本段未重新查核。
- 模型同條件值（工作簿 Calib J 節同一條式，H200 規格、DeepSeek-V3 架構、EP64、MTP 3 草稿；`q2_results.json`）：1,656／1,447／1,109／640，**模型 ÷ InferenceX＝1.05／1.17／1.19／0.87**；每 GPU 序列 11.5／5.4／2.4／0.9。不用 MTP 時，30 tok/s 為 0.96，50 tok/s 以上不可達；EP8 單機時固定延遲 34.8 ms，30 tok/s 不可達。
- 讀法：Hopper 在中等互動速度、小批次下，模型與旁證一致，**看不到大批次點的 3–4 倍低估**。這是「差距屬於大批次或部署型態，而不是 Hopper 的世代水準」的主要依據。但這個依據只有旁證，而且 Hopper 的 η_d 倍數 C67 的區間本來就參考過 InferenceX，兩者不完全獨立。

## 5. Q4 用 v10.2 工作簿量化

做法：
- 複製 v10.2，在 scratch 中改輸入或暫時把公式改成常數，再以 LibreOffice 重算。
- 基準情境重現 v10.2 的存檔值：`L1_MFleet` 0.4073，Calib J 節 0.338／0.372／0.266／0.267／0.261。
- (b) 的 η_d 與批次互相依賴：η 變大，SLO 下的批次就變大。所以先在 Python 用工作簿同一條式求固定點，再把各欄的 η_d 寫成常數。重算後，工作簿算出的批次與固定點一致（`verify_B`，不一致 0）。
- (b) 的變數取「每 GPU 每步處理的 token 數」：序列數 ×（草稿數＋1）。MTP 的草稿 token 也要經過矩陣運算。
- 形狀：
  - 早升 B1：76 token 以下倍數 1，即 GB300 擬合點的上緣；到校準點時達到校準倍數（Hopper 128、GB200 1,017），中間取對數線性。
  - 晚升 B2：410 token 才開始上升，即 GB300 MLPerf server 在模型倍數為 1 時仍有 0.90。

補充情境（`q4_results.json`）：
- MLPerf offline（取消速度下限）：模型 GB200 3,856（÷6,752＝0.571）、GB300 5,802（÷8,987＝0.646）。在 B1 下，GB200 offline 升到 10,547（1.56 倍）。
- TensorRT-LLM H200 8 GPU 條件（ISL 1K／OSL 2K、11.35 tok/s、EP8）：模型 567 ÷ 1,436＝0.39（模型批次 54，實測每 rank 128）。
- B1 套到全部世代（檢查）：GB300 server 升到 2.65、VR200 interactive 升到 2.05，驗證失敗增為 11。所以若 (b) 是普遍的物理效應，現有的 GB300 MLPerf 點（模型倍數 1 時 0.70–0.90）會被打破。這也支持「差別在部署型態，不在批次」。

讀法：
1. **哪一個假設能同時解釋校準點與驗證點**：都不能單獨做到。
   - (a)：校準點與驗證點幾乎都不動。
   - (b) 早升：校準點與 LMSYS GB200 對上，但 Hopper 兩個驗證點仍是 0.27，V2 失敗。
   - (b)＋(a2)：可以再對上 LMSYS H100（0.99），但 DeepSeek 線上仍是 0.34。
   - 世代常數：對上全部大批次點，但三個 MLPerf 上限都失敗。
   - **沒有一個只看批次的形狀能同時對上大批次的開源點和 MLPerf 點。**
2. **對服務 SLO 下的 m**：服務批次小（每 GPU 每步 Hopper 4–35 token、GB200 23–197 token），所以：
   - (a)：0（上限 −0.065，但證據顯示小批次時重疊反而變慢）；
   - (b)：0（晚升）到 −0.048（早升，只透過 GB200 的 Luna、Sol 兩欄）；
   - 世代常數：−0.235。
3. `IF_AllocRDGW` 只有在 η_d 改動波及 Perf_Batch（研發用的大批次工作：RL rollout、蒸餾、合成資料）時才會變動（0.2402 → 0.1626）。把大批次倍數只放進既有的 `CAL_BatchEtaD` 時，`L1_MFleet` 完全不變，只有 `IF_AllocRDGW` 變動。η 校準報告第 5 節 E1 試算中 `IF_AllocRDGW` 的 0.1626，來源就是這一條路徑。

## 6. 對建置段的建議（只寫建議，不做決定）

1. **不建議實作 (a)**，即改寫 EP 通訊重疊。模型已經假設完全重疊，改了也不會動。真正需要處理的是 Hopper 的 EP 通訊下限：只有在 η_d 提高後，這個下限才有作用。精修方向有三個：
   - EP 通訊效率 0.7，DeepSeek 理論式相當於 1.0；
   - 計入 8 個專家（論文計 9 個）；
   - 層數 61（其中 3 層非 MoE）。
   這些可以在 (b) 決定後一併檢視。
2. **大批次的效率差距建議放在「批次口徑」**：用既有的 `CAL_BatchEtaD`（Calib 第 156 列，X10，只作用於 Perf_Batch），而不是改服務側的 C67／D67。
   - 理由：服務 SLO 下的小批次點（MLPerf interactive、InferenceX 旁證、MLPerf v5.1 對齊）與現行 η_d 一致；大批次點一致偏低 3–4 倍。
   - 試算：`CAL_BatchEtaD` 設為 Hopper 3.74、GB200 3.04 時，`L1_MFleet` 不變，`IF_AllocRDGW` 0.2402 → 0.1626。這會碰到 η 校準工作單的「不得變」清單，需先判斷。
3. **若仍要讓服務側 η_d 隨批次變化**，建議用兩段式（小批次段＝現行擬合；大批次段＝校準值），切換變數用「每 GPU 每步 token 數（含 MTP 草稿）」。切換點有兩個候選：76（早升）、410（晚升）。兩者對 m 的差別只有 0 到 −0.05，但早升會讓 V2 失敗。
4. **校準點**：
   - Hopper 大批次：DeepSeek profile 2,324；
   - GB200 大批次：vLLM 10.1K。
   兩者都屬「寬 EP、PD 分離、decode-only」型態。
5. **保留作驗證**：
   - 同型態：DeepSeek 線上 1,850（V15，與校準點同公司，相關性高）、LMSYS V7、V8；
   - 不同型態：MLPerf v6.0 offline（新，同一來源三情境，建議新增 GB200 6,752、GB300 8,987 作為「模型 ÷ 實測」的對照）、TensorRT-LLM H200 1,436（新）；
   - 小批次：MLPerf interactive V4、V5、InferenceX（旁證）。
6. **在動任何 η_d 之前**，先決定 V2 的判準：MLPerf server 的 80 ms 是 p99，模型把它當平均。

## 8. 待 Project 判斷

1. **差距的歸屬**：世代水準（常數倍數，m 約 0.17）、批次（m 0.36–0.41），或部署型態（只放進批次口徑，m 0.41）。本段的證據較支持後兩者，但 Hopper 小批次只有旁證。
2. **V2（以及 V1、V3）的「模型 ≤ MLPerf server」是否為硬上限**：MLPerf server 的 TPOT 80 ms 是 p99，模型拿它當平均每步時間。TensorRT-LLM H200 在相近的每用戶速度、無尾端限制時，吞吐是 MLPerf v5.1 的 2.6 倍。
3. **`CAL_BatchEtaD` 是否改用大批次校準值**（Hopper 約 3.7、GB200 約 3.0）：會使 `IF_AllocRDGW` 由 0.2402 變為 0.1626，與 η 校準工作單的「不得變」清單衝突。
4. **Hopper 固定延遲是否重複計算 EP 通訊**：每層延遲 241.8 µs 與 DeepSeek 論文的雙 micro-batch 每層通訊 241.92 µs 數字相同，而 EP 通訊另外計在每序列項裡。
5. **新增驗證點**：MLPerf v6.0 offline（GB200 6,752、GB300 8,987）、TensorRT-LLM H200 1,436（每 rank 128、11.35 tok/s/user）。
6. **補查**：
   - Hopper 寬 EP 的同源批次掃描；
   - MLPerf server 平均 TPOT；
   - SGLang TBO 消融的 EP 寬度與通訊占比（數字只在圖中）；
   - Perplexity 頁面（被擋）；
   - InferenceX 吞吐口徑（總 token 或輸出 token）的直接確認。
