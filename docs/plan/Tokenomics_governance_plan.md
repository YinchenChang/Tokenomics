# Tokenomics 資料架構與治理規劃書 v0.3（定案）

**Tokenomics 的目標，是成為「AI 技術 → AI 算力需求（投入／支出）→ AI 算力收入」這條供應鏈的事實基礎。** 所有已取得的原始訊息（未經計算、不是假設）都集中在第 0 層 Source。Tokenomics 各頁，以及以後所有用到 AI 技術或算力數據的產業與個股模型，都從 Source 取用或推算。Source 沒有的資料就去找。所有新訊息，不論是建模時找到的，還是 Andy 主動提供的，都先登錄 DB_Evidence，與 Source 比較後擇優更新 Source。

## 1. Andy 的原話與本規劃採用的定義

| Andy 原話（2026-10-02） | 本規劃的定義 |
|---|---|
| 「已取得的原始訊息(非計算過、非假設)都放在Source(第0層)」 | Source 只存放原始訊息。計算值（Derived）、Claude 的假設（Assumed）、類比推估（Analogy）、決策（Decision）都不放 Source |
| 「其他頁(包括以後下游)需要的資料要嘛從Source取來用或算」 | 模型頁的原始數據一律以公式連結 Source；下游可以直接取用 Source，也可以取用推算結果（Interface） |
| 「source沒有可以自己去找，回來(新訊息應該就先放進DB_Evidence)要跟source比，用比較好的並放入source」 | 固定流程：找 → 登錄 DB_Evidence → 與 Source 比較 → 擇優寫入 Source（第 4 節） |
| 「舊的先保留，以免一直找爛資料來比，可討論」 | 被取代的 Source 紀錄保留並標為 Superseded；不採納的證據保留在 DB_Evidence，作為「已看過」清單。已定案（第 9 節 D1） |
| 「非其他頁找的新訊息(通常就是Andy主動加/問的)也先放DB_Evidence，一樣要比要更新進Source」 | Andy 提供的訊息走同一條流程，沒有捷徑 |
| 「Andy的資料來源就是Andy，被證偽前擁最高等級」 | Source 的來源等級中，A 級＝Andy，排序最高。只有在被證偽時才降級（第 3 節） |
| 「主要就是我主觀看法，自行承受後果」 | Andy 的主觀看法登錄為 Source 紀錄，標記為 Andy，並保留原話 |
| 「不要考慮法遵相關事宜」 | 不建機密分級與存取權限機制。所有資料同在一本活頁簿與公開 repo |
| 「以後其他產業或個股要用AI技術/算力相關數據都是用第1點那個流程」 | 所有專案模型（OpenAI、CRWV、Nebius、Oracle 等）用到 AI 技術或算力數據時，都經由 Tokenomics 的 Source 與 DB_Evidence 取得，不各自維護 |

### 2.1 資料分類

| 類別 | 定義 | 存放位置 | 標記 |
|---|---|---|---|
| Evidence | 尚未判定、或判定不採納的訊息 | DB_Evidence | 判定欄 |
| Source | 已採納的原始訊息 | SRC_* | 來源等級＋立場（第 3 節） |
| Andy | Andy 的看法或資料 | SRC_*（來源＝Andy） | A 級 |
| Analogy | 由 Source 中的可比對象推估 | 模型頁藍字，附區間、可比對象的 SRC_ID 與差異說明 | Analogy |
| Assumed | 沒有實證、但模型必須使用的值（Claude 提出） | 模型頁藍字，附區間與理由 | Assumed |
| Decision | Andy 對口徑、範圍、方法的選擇 | Decisions 頁；模型頁的選擇格附決策 ID | Decision |
| Derived | 公式推導的結果 | 模型頁公式；常用者另列於 L1 頁（第 1 層，即時公式，不貼值） | — |

這裡和建議書有兩處不同：

1. 建議書把 Analogy 與 Assumption 放進治理層的登錄表。本規劃讓它們留在使用它們的模型頁，因為它們不是原始訊息；Checks 負責檢查區間與 ID 是否齊全。
2. 建議書沒有 Andy 這個來源類別。

### 2.2 下游取數規則

建議書禁止下游直接引用 SRC_*。本規劃依 Andy 第 1 點，**允許下游直接取用 Source**，條件是：

- 以 SRC_ID（具名範圍）引用，不引用儲存格位址；
- 只取用狀態為 Active 的紀錄；
- 推算結果取 L1（標準條件下的常用值）或 Interface（完整構件），不在下游重算 Tokenomics 已有的推導；
- 下游只自算公司特有的那一步。例如 CRWV 以 Interface 的資本支出加上自己的 WACC 重算持有成本，而不是從原始資料重走整條推導鏈。

## 3. Source 的設計

### 3.1 分頁（依欄位結構拆分）

| 分頁 | 內容 | 特有欄位 |
|---|---|---|
| SRC_HW | 晶片與機架的規格、功率、價格 | 精度（FP8／NVFP4）、dense／sparse、功率模式 |
| SRC_DC | 廠房資本支出、電價、PUE、折舊慣例、資金成本 | 地區、電力口徑（IT／設施） |
| SRC_Model | 模型架構、訓練揭露 | 總參數、啟用參數、token、GPU 小時、精度 |
| SRC_Perf | 推論與訓練量測（InferenceX、MLPerf、自揭） | 平台、軟體、ISL／OSL、互動速度、輸出或總 token |
| SRC_Price | API 與 GPU 出租價格 | 輸入、快取、輸出、尖峰／離峰、幣別、日期 |
| SRC_Cap | 能力指數、METR、ARC 等 | 指數名稱與版本、測試條件 |
| SRC_Demand | 算力需求與支出揭露（實驗室支出、token 量、GW 規劃、營收） | 公司、期間、GW 口徑 |
| SRC_Harness | harness 與 agent 量測 | 任務、harness、成功率、token、成本 |

**共同欄位**：SRC_ID、指標、數值（數字格）、低、高、單位、口徑、適用對象（世代、模型、公司）、日期、來源（出處或「Andy」）、來源等級、立場、一手／二手、查核等級、狀態（Active／Superseded／Alt）、取代者、Evidence ID、Andy 原話（A 級時填）。

**拆頁規則**：欄位結構不同就拆頁，不看筆數。新增分頁屬於工程類事項，由 Claude 決定。

**與現有 Sources 頁的關係**：現有 61 筆是文字摘要，0 格數值。這些紀錄會拆成數值紀錄（預估 120–200 筆）並遷入各 SRC 分頁；原頁更名為 Sources_Legacy 保留到遷移完成。

### 3.2 來源等級與立場

| 等級 | 定義 |
|---|---|
| **A** | Andy。被證偽前排序最高 |
| **1** | 一手：原頁、原始規格表、論文、官方揭露、稽核結果，而且已經讀過原文 |
| **2** | 二手：報導、轉述、第三方整理 |
| **3** | 未查核：模型內建知識、只見摘要 |

立場與等級是兩個獨立的軸：中立，或利害關係方（須寫出是哪一方、它的誘因）。SemiAnalysis（含 InferenceX）的規則不變：必須另有第二來源佐證。

### 3.3 「較好的」比較規則

只有**同一指標、同一口徑**的紀錄才互相比較。口徑不同時，兩筆都保留，新紀錄的狀態設為 Alt。

同口徑時，依以下順序判定：

1. 來源等級高者勝，A 級最高。
2. 等級相同時，中立方勝過利害關係方。
3. 仍相同時，量測條件較接近模型口徑者勝，例如生產環境勝過基準測試。
4. 仍相同時，日期較新者勝。

**例外：多家獨立估計（2026-10-02 增訂，交接文件 G13）**：同一指標、同一口徑，但由不同機構各自獨立推估者（例：VR200 機架價格 Morgan Stanley 7.8、Bernstein 9.09），不套用上述第 4 步「日期較新者勝」。全部並列（Alt，不取代）；模型基準取中位數、低取最小、高取最大；Andy 可個別覆寫，並登錄決策 ID。理由：獨立推估晚發布不代表較準。

**A 級的證偽**：

- Claude **不會**自動取代 A 級紀錄。
- 當一筆 1 級中立證據落在 Andy 的數值或區間之外，Claude 把它登錄為「待 Andy」，並說明差距與影響。
- 由 Andy 判定是否證偽。判定之前，A 級紀錄維持 Active。

## 3A. 第 1 層：常用推算值（L1）

**問題**（Andy 2026-10-02）：由 Source 原始資料推算、普遍常用的數字，例如 1 GW VR200 DC 總建置成本、理想上 1 GW VR200 服務高階模型的營收區間，應該存起來，還是由取用者每次自算？

**決定**：存放，但不放進 Source 本身；以即時公式維持，不貼值。

**理由**
- **自算的成本不在算術，在口徑。** v5.10 溯源結果：1 GW VR200 建置成本經 23 個公式格、依賴 16 個輸入；1 GW VR200 Sol 理論營收經 1,189 個公式格、最多 290 個輸入（語法依賴上限）。取用者不可能每次正確重走。
- **本 Project 已有實例。** E001 是 Hopper 峰值的口徑錯誤（BF16 0.989 對 FP8 1.979 PF），只修一處就全部更正。D8 是 OpenAI v0.5 自建 roofline 與 Tokenomics 分歧，後來改為連結 Interface。
- **AI 重新產生數字很便宜，正是自算的風險。** 版本會快速分歧；驗證只做一次，但要有地方讓所有人共用那一次驗證。
- **不放進 Source。** Source 的規則是「非計算過」。推算值若與原始值共用 SRC_ 名稱，就無法區分黃仁勳說的每 GW $50–60B（原始，利害關係方）與本模型推算的 $47.6B；兩者的比較正是最有資訊量的地方。
- **不貼值。** 貼值會在原始資料更新後悄悄過時。

**L1 頁的設計**
- 頁名 `L1`，具名範圍前綴 `L1_`。**取代第 8f 節原定的 Answers 頁與 AN_ 前綴**：Answers 的問題成為 L1 的列，不另建一頁。
- 每列欄位：L1_ID｜指標或問題｜條件（世代、層級、成本情境、利用率）｜基準值｜區間｜區間的定義｜讀法｜主要驅動｜最弱輸入的標記｜對應外部原始值（SRC_ID）｜推算 ÷ 外部｜判讀｜具名範圍｜所在頁與列｜未能回答的部分。
- 數值欄一律為公式，連結模型頁或 Interface。
- **Checks 的比對功能移入 L1。** 目前 Checks 寫死的 45 格外部參照，改為 L1 列中連結 SRC 的對照欄。Checks 只保留完整性與佇列，並以 INFO 彙總 L1 中落在外部區間之外的列數。
- **入選條件**（任一即可）：兩個以上取用者使用；Andy 曾提問或在報告中引用；有對應的外部主張（SRC 中有可比的原始值）。
- **與 Interface 的分工**：Interface 是完整推算構件（約 167 個名稱 × 15 欄），供下游的機器連結；L1 是精選的約 20–40 個常用數字，附條件、區間與外部對照，供人閱讀，也供下游引用標準數字。L1_ 名稱與 IF_、SRC_ 一樣，適用第 6 節 Stage 3 的契約規則。

**第一批 L1 列**（Stage 1 切片一建立；其餘隨切片與 Block 6 補入）
- 每 GW 資本支出（各世代；對照黃仁勳 $50–60B／GW 等）
- 每 GW 年經濟持有成本；每 GPU 小時持有成本（對照 SemiAnalysis、CoreWeave 公開價）
- 每 MW IT 廠房資本支出（對照 JLL）
- 各層級每 M token decode 成本（VR200、GB300）
- 每 GW 理論營收區間（VR200 × 各層級；即 Andy 舉例的「服務高階模型的營收區間」）
- Block 6 的第一批 9 題（第 8f 節），在 v5.13 補入

## 4. 新訊息流程

1. **需求出現**：某個模型頁或下游模型需要一個數值，或 Andy 提供、提問。
2. **查 Source**：已有 Active 紀錄就直接取用，流程結束。
3. **查 DB_Evidence**：確認這筆資料是否已經看過，或曾經判定不採納。
   - 若曾不採納、而且這次沒有新的理由，就不重複處理。這一步是為了避免一直找爛資料來比。
4. **蒐集**：找到的每一筆候選訊息都登錄 DB_Evidence，記錄 E_ID、主張、數值、單位、口徑、出處、等級、立場。
5. **比較**：依第 3.3 節比較，判定結果為以下四種之一。
   - **取代**：新紀錄成為 Active，舊紀錄改為 Superseded 並記錄取代者。
   - **並列**：口徑不同，新紀錄設為 Alt。
   - **不採納**：記錄理由。
   - **待 Andy**：涉及 A 級紀錄，或改變結論的幅度超過門檻。
6. **寫入與重算**：寫入 SRC；模型頁經公式自動更新；CC 產出逐格差異；Checks 必須為 0 個 ERROR。
7. **登錄結果**：DB_Evidence 記下判定、處理版本與受影響的 IF_ 名稱。

**誰判定**：步驟 5 屬判斷類，在 chat 端執行。只有「待 Andy」的項目提交 Andy。步驟 1–4、6、7 中屬於工程的部分，由 CC 依既有分工執行。

## 5. Checks 的角色

| 角色 | 檢查 | 等級 |
|---|---|---|
| **完整性** | 模型頁中，標為原始數據（Verified／Interested-party）的藍字格沒有連結 SRC，也就是原始數據寫死在模型頁 | ERROR |
| | Analogy 或 Assumed 參數缺區間、缺理由；Analogy 缺可比對象的 SRC_ID | ERROR |
| | Decision 選擇格缺決策 ID | ERROR |
| | 同一指標、同一口徑有兩筆 Active | ERROR |
| | SRC 紀錄沒有任何 Evidence ID | ERROR |
| | 模型或下游引用的 SRC 紀錄不是 Active | ERROR |
| | 利害關係方紀錄缺第二來源（SemiAnalysis 規則） | WARN |
| | 3 級（未查核）紀錄被 load-bearing 參數使用 | WARN |
| | L1 數值欄不是公式（貼值） | ERROR |
| **比對** | 移入 L1 頁（第 3A 節）。Checks 只以 INFO 彙總 L1 中落在外部區間之外的列數 | INFO |
| **佇列** | DB_Evidence 中「待判定」與「待 Andy」的筆數；審查日已過的 SRC 紀錄 | INFO |

CI 讀取 ERROR 總數，必須為 0 才能合併。

## 8. 節奏與版本

- **事件驅動**：沒有固定的週、月例會。新訊息隨時進 DB_Evidence。
- **版本規則**：
  - 只新增 Evidence、不改任何 SRC Active 值 → 修補版（例如 v5.11.1）；CC 只需確認 parity 不變。
  - SRC Active 值改變，或公式改變 → 次版（v5.12）。
  - 指標定義、IF_ 或 SRC_ID 契約改變 → 主版（v6）。
- **每次升版時**，Checks 的佇列項目（待判定、待 Andy、審查日已過）列入交接文件。
