## 0. 一句話結論

**公式抄寫沒有問題，但定義與驗證有系統性問題，而且有一部分已經影響到下游契約名稱。**

- 公式抄寫層面：斷引用、欄位錯位、循環參照都是 0；以 Python 依工作簿公式重算約 15,000 格，與檔內數值 0 不符。
- 定義與驗證層面，問題集中在五類：
  1. 時點與世代混用
  2. 殘差與倒推被當成估計，還有循環驗證
  3. 同一個名稱有兩種定義（下游正在讀）
  4. 分母與口徑不一致
  5. 「不可達」被當成 0

## 3. 決策清單（16 題）

格式：問題｜選項｜**建議預設**｜影響｜出處。

### A. 定義原則（先決定，其他題依此展開）

**D1 世代欄代表什麼（Z1）**
- 選項：
  - (a) 維持「同一 2026 模型跨硬體比較」，作為截面定義。
  - (b) 每個世代欄代表「該世代服務期間的代表模型」。
- **建議 (a) 並明示**：Interface 各世代輸出一律加註「固定模型口徑（2026 模型快照）」。凡是要回答「某年度實際如何」的計算，改用 D2 的年度口徑，不從世代欄讀。
- 理由：(b) 需要為每個世代另建一套 Arch 與 Serving，工程量大、新增的 Assumed 多，而且下游讀世代欄的用途本來就是截面比較。
- Andy 2026-10-15 指出模型會隨時間變大，這一點以 D2 處理。

**D2 年度計算一律用該年度口徑（Z2）**
- 原則：凡標示「2025 年度」的計算，硬體組合、單價、token、模型、研發世代全部取 2025 年的值；不得混入 VR200 或 2026 牌價。回本判讀的成本與實收必須同一世代口徑。
- **建議採用**。
- 影響最大的一題：m_fleet、`IF_AllocQ1`／`Q2`、`IF_AllocRDGW`、回本所需單價、FleetMargin 都會變動，需要年度輸入（見 D3）。

**D3 2025 機隊世代組合（Z2）**
- 現值：Hopper 60%、GB200 40%、GB300 0%。沒有來源；而 2025-10 已有大規模 GB300 部署（Azure 為 OpenAI 部署，公開資料可查）。
- **建議**：發外部搜尋工作單（A 段）取得組合與區間；在那之前，把區間放寬到包含 GB300。
- 影響：m_fleet −51%～+170%，是 m 最大的單一驅動因子。

### B. 呈現與驗證原則

**D4 殘差與倒推要明示（Z3）**
- 原則：由「營收 ÷（token × 單價）」或「使某值不變」得出的量，一律標「殘差」或「倒推」，不以「估計」呈現；缺口分解改為「已解釋／未解釋」。
- **建議採用**。只改標籤與 Checks 的呈現，不改數值。

**D5 驗證必須能失敗（Z4）**
- 原則：恆等式和擬合點重現改標「恆等式（非驗證）」，從 Checks 的驗證計數中移出。校準過的輸入，不得再用同一個目標來對照。
- **建議**：
  - MLPerf 作為第二校準來源（模型比 MLPerf 低 30–51%），擬合改為「擬合點＋獨立驗證點」。
  - RL rollout 與 harness 輪數，各找一個獨立的對照目標。
- 影響：η_d、η_p 的區間會變寬；`IF_CostPre` 的敏感度 +100%／−33% 將正式顯示出來。

**D6 Hopper 效率倍數（Z3、Y8）**
- 現值：η_d 1.5、η_p 依峰值比，目的是「使 Hopper 產出不變」。
- **建議**：保留現值、標「倒推」、區間放寬到 1.0–2.0；用 MLPerf 的 Hopper 結果，或 2025 年 Hopper 的實測，取得獨立依據。
- 影響：m_fleet +90%／−27%。

### C. 下游契約名稱（最急，影響已在用的公司模型）

**D7 `_Life`／`_Prod` 統一定義（Z5）**
- 選項：
  - (a) `_Prod` 一律重解 SLO（物理上正確）。
  - (b) 一律線性 ×0.85（簡單，但與 SLO 不一致）。
- **建議 (a)**，並以 `IFW_*_Life` 為唯一的 `_Life`；`IF_*_Life` 保留一個版本作為過渡別名，之後刪除。同時修訂契約第 2 條。
- 影響：下游讀到的數值會變動 19–51%，**觸發下游同步**。CoreWeave 正在自行測試，需要先通知。

**D8 「不可達」的語意（Z7）**
- 原則：不可達一律以文字旗標表示，從組合加權中排除該層級，不得變成 0；下游契約寫明「文字＝不可用」。
- **建議採用**。
- 影響：Training 的 0 GPU 小時、Q1 的不單調，以及 28–39 個契約名稱的讀法。

### D. m 的分子與分母

**D9 m 的單價與 token 同口徑、同年度（Z6、Y6）**
- 原則：快取命中同時進價格與產能；免費占比統一用 token 口徑；ISL／OSL、每提示 token、κ 三者對齊，價格端也套用 κ。
- **建議採用**，與 D2 同一版處理。
- 影響：m ±17–100%；攤提閉合 0.82–0.88 改善為 1。

**D10 計價倍數的成本口徑（Z6）**
- 現值：1.3。依據的毛利是會計口徑，分母卻是經濟口徑持有成本，兩者相差 0.73 倍。
- **建議**：分母改為會計口徑，或把依據換算成經濟口徑，兩者擇一並寫明。
- 影響：m_fleet ±23%。

**D11 回本溢價與攤提的分母（Z6）**
- **建議**：「回本所需溢價」改用付費 token 作分母。
- 影響：`IF_FullCostDefault_Luna` +75–94%，下游契約名稱會變動。

**D12 L、m 的作用方式（F10）**
- 現況：控制值 L＝m＝1 進 `_Life`；自算的 L 0.64、m 0.79 只並列顯示。
- 選項：
  - (a) 維持
  - (b) 加一欄「自算值情境」
  - (c) 直接改用自算值
- **建議 (b)**。(c) 會讓殘差回流到輸出，形成循環。

### E. 輸入值與來源

**D13 暫定值（Z8）**
- 對象：Serving C17（0.6）、C18（1.0）、C28（0.85），以及實際利用率 0.35。
- **建議**：每格改為明示的 Assumed 區間，並在 Decisions 記錄「暫定、待證據」；由 Andy 給基準值，或先接受現值。

**D14 研發與服務 GW 的口徑（B01、B02、B09；也就是索引中原候選 (a) 的四個規模係數閉合）**
- 現況：token 路線與支出路線差 4.9 倍；自下而上與 ScaleRD 差 10.8 倍；Astra 預訓練比 Epoch 估計低 14.6 倍。Q1 隨口徑落在 0.09–0.52。
- **建議**：服務 GW 以支出路線為主口徑（token 路線正是 m 要檢驗的對象，不宜同時當作輸入）；Astra 預訓練把 Epoch 估計列為區間高端。

**D15 來源補齊與證據積壓（Z9）**
- 對象：311 列無來源（其中 m 路徑上 49 格為高嚴重度，優先處理）；證據積壓 102 列（其中 48 列是遷移紀錄）。
- **建議**：
  - m 路徑上的 49 格，至少補決策編號，或補一個來源。
  - 證據積壓逐列判定一次。
  - L1 外部對照欄的單位修正與過期說明，屬於工程類，直接處理。

## 6. 限制

- 每一段都由單一代理判讀，沒有第二人抽查。「沒發現問題」不等於「已證明正確」。
- 擾動只做單一輸入，沒做交互作用。部分端點是自訂的（例如世代組合取 0%／100%）。
- 物理推導（roofline、批次、注意力 FLOPs）只檢查量綱、口徑與數量級，沒有重新推導。
- 「倒推」的判定依據是工作簿的說明文字；沒查到紀錄，不等於不存在。
