## 4. E1 為什麼沒有寫入（停損）

**Hopper（DeepSeek profile，H800、批次 128、EP128、KV 4K，目標 2,324）。** 複本列依 Calib H 節公式計算：每序列每步時間取「算力、KV 讀取、EP 通訊」三項最大。算力項靠 η_d 縮小，但 EP 通訊項（0.2975 ms，與 η_d 無關）是下限。C67 無論調到多大，產出最多只到 2,187 tok/s/GPU（目標的 0.94），**沒有解**。在 DeepSeek profile 條件下，即使 η_d 無限大，Hopper 也只達目標的 0.94（EP 通訊下限），所以沒有解，不寫入 C67。（2026-10-16 更正：原稿寫「有效算力遠高於 GB300，不合物理」並不正確。實際比較：Hopper 在該條件下有效算力 0.318 PF，低於 GB300 的 0.536 PF；只有 GB200（1.086 PF）高於 GB300。）
- 另一種讀法（C68 吸收差距，C67 維持 1.2）：同樣沒有解（EP 通訊下限未動）。不採用。
- 可能的原因（供判斷）：官方 profile 的 EP 通訊在微批次間重疊，本模型的通訊項為不重疊；若改寫通訊重疊假設則屬公式邏輯，須 Project 判斷。

**GB200（vLLM WideEP，目標 10,100）。** 模型 ÷ 目標 ＝ 0.372，不在 0.9–1.1，需新增倍數。所需倍數約 3.04（EP8）至 2.79（EP32），對應 η_d 約 10%，GB200 有效算力 0.358 → 1.09 PF/GPU，高於 GB300 的擬合值 0.536，且使 V5（GB200 interactive 上限檢查）轉為失敗。依停損規則不寫入。

**C67／D67 的區間**：由所需倍數反推列在 Calib J 節（`達標所需 η_d 倍數`）。因未寫入，不登錄新區間；請在 Project 判斷後一併處理。
