## 4. K4 拆解：Hopper 欄攤提與全成本

做 K1–K3 後重算 v6.1 → v6.3。三個成本情境欄（Luna）各自拆成：(a) 排除 Astra 的 token（由上而下總量與由下而上總量都不含 Astra，Luna、Sol 自身的由下而上攤提不變）；(b) 重新正規化（Luna、Sol 的 token 分母改變，其自身由下而上攤提下降）；(c) K1（只動單價，不進 Unit_Cost 與 Amortize）。

|---|---|---|---|---|
| 成本情境 1（Hopper 第 1 欄） | 2.043 → 9.329 → 13.827（v6.3 同） | 0.09082 → 0.03608 | 0.18556 → 0.84726 → 0.49892 | 0.33076 → 0.99246 → 0.64412 |
| 成本情境 2（Hopper 基準成本欄） | 2.043 → 9.328 → 13.827（v6.3 同） | 0.12977 → 0.05156 | 0.26513 → 1.21054 → 0.71285 | 0.47258 → 1.41800 → 0.92030 |
| 成本情境 3（Hopper 第 3 欄） | 2.043 → 9.328 → 13.826（v6.3 同） | 0.22286 → 0.08854 | 0.45531 → 2.07891 → 1.22420 | 0.81158 → 2.43518 → 1.58048 |

讀法（以 Hopper 基準成本欄為例）：

- (a) 排除 Astra：由下而上攤提總量 2,369 → 340（−86%），由上而下訓練總量只從 4,840 → 3,171（−34%），因此 scale（由上而下 ÷ 由下而上）由 2.04 升到 9.33。Luna 預設攤提 0.265 → 1.211。
- (b) 重新正規化：Luna 自身的由下而上攤提 0.1298 → 0.0516（−60%，token 分母變大），scale 再升到 13.83；兩者相乘使預設攤提 1.211 → 0.713。
- (c) K1：0。
- 方向相反的原因：`IF_FullCost_Luna`（不乘 scale）只含自身攤提，隨 (b) 下降（0.337 → 0.259）；`IF_AmortDefault_Luna`（乘 scale）隨 scale 上升。兩者同源，不矛盾。
- 不明殘差：0（(a)、(b) 的乘積與實際 v6.2 值逐欄相符）。
- 值得注意：Astra 被排除後，它的由上而下訓練成本並未同比例消失，改由 Luna、Sol 吸收（scale 2.04 → 13.83）。這是否合理屬判斷，見第 7 節第 2 項；本段不修。
