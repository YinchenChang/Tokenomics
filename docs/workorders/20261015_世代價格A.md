## 1. 定位原則

- Tokenomics 衡量**產業基準**：代表性的硬體、成本、產出、價格與其變化速度。不呈現任何個別公司的簽約價、合約組合、機隊結構或客戶條件。
- 公開市場價格點（現貨指數、公開報導的牌價、已揭露的長約單價）屬產業級價格資料，可以蒐集；但只記錄「價格點」本身，不記錄該公司的合約組合、客戶或公司指引。
- 公司模型（CoreWeave、Nebius、Oracle 等）的收入、成本、估值不在範圍內。

## 3. 工作項目（依序；每完成一項：更新進度檔 → commit → push）

### 步驟 1：確認 q 的定義（最重要，先做）

回答：q（`L1_TokMW_Gen_ratio_*`）是在什麼條件下算出的產出比？
- Arch 頁 Luna／Sol／Astra 三個層級的模型參數（參數量、啟用參數、層數、維度、上下文等）**是否跨世代固定**？逐格列出 q 公式鏈引用到的 Arch／Serving／Calib 格，看是否有任何一格依世代變動。
- 若固定：q＝「同一個模型、新硬體」的產出比 → 與之配對的價格口徑只能是「同等能力 token 價格」。
- 若不固定：寫出哪些參數隨世代變、怎麼變。
- 報告中寫一段（不超過 10 行、非工程語言）：「q 對應哪一種價格口徑，理由」。這是給 Project 判斷 Q3 的依據，**不要自行決定 Q3**。

### 步驟 2：E338–E341 一手確認（Q7）

- 從 DB_Evidence 取出 E338–E341 全部欄位。
- 逐筆找一手來源（官方牌價頁、官方公告、官方部落格；可用 Wayback Machine 的官方頁快照）確認數值與日期。每筆標：一致／不一致（附正確值）／找不到一手來源（說明找了哪些地方）。
- 用確認後的數值重算 E341 的年變化率（各期間、各系列），與原值對照。
- 「找不到」與「不存在」分開寫。

### 步驟 3：價格序列蒐集（Q5）

三組分開，**不得混用**：

| 組 | 口徑 | 例 |
|---|---|---|
| (a) | 同等能力 token 價格 | 達到某固定基準分數（例如 MMLU 或其他公開基準的固定門檻）所需的最低 token 價格隨時間變化；Epoch AI 等公開整理可用，但須回溯到其原始牌價來源 |
| (b) | 層級牌價 | OpenAI／Anthropic／Google 各層級（前沿、中階）旗艦模型上市時的每 M token 牌價（輸入、輸出分開） |
| (c) | 算力租賃價格 | 每 GPU 小時或每 MW：A100、H100、B200／GB200、GB300、VR200（有資料時）；**隨需、預留、長約分開**；時點取各世代上市後 0–6 個月與現價 |

每筆欄位：數值、單位、世代（或模型）、層級、時點、來源名稱、URL、文件日期、擷取日、標記（Verified／Interested-party／Analogy／Assumed／Derived）、利害關係說明（若 Interested-party）。

規則：
- SemiAnalysis 不可單獨引用；同源轉載不算獨立來源。
- 公司揭露的長約單價可記為價格點（標 Interested-party），但不記該公司的合約組合或客戶細節。
- 目標數量（參考，不是硬門檻）：(a) 至少一條連續序列；(b) 每家至少 3 個時點；(c) 每世代每層至少 2 個點。找不到的格子寫「已搜尋，未找到」並列出搜尋過的管道。
- 唯讀蒐集可分給最多 3 個並行子代理（各負責一組、各寫自己的暫存檔，由你合併）；子代理也用 Sonnet。

### 步驟 4：世代上市間隔（Q4）

三對相鄰世代：Hopper→GB200、GB200→GB300、GB300→VR200。
- 上市時點以「量產出貨或雲端開始供應」為準，不用發表會日期；兩種日期都記下。
- 每對給基準與區間（標 Analogy 或 Verified），附來源。

### 步驟 5：實算對照

- 用步驟 3 的序列，對每一對相鄰世代、三種口徑各算一次「上市對上市」價格變化，再乘上 q 得到世代每 MW 收入指數（(c) 組本身已是每 MW 或每 GPU 小時，換算方式寫清楚；每 GPU 換每 MW 用 Excel 既有的每 MW GPU 數，註明引用格）。
- 與 q × (1+g)^Δ（g＝−25%、−10%、+5%；Δ 用步驟 4 基準與區間）的推算值並列。
- 另列「指數 ÷ 每 MW 持有成本比」（回本餘裕），成本比用 L1_HoldEconMW 各世代比值。
- 列出兩個門檻：收入指數＝1 與回本餘裕＝1 各需要的年價格變化率，並標出步驟 3 的實證值落在門檻哪一側。
- 資料不足以實算的組合，寫「無法實算」並列出缺哪一個輸入。
