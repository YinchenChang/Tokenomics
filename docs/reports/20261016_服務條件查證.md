## 2. Q2 生產環境的批次與並行度

換算關係（恆等式，Derived）：**每 GPU 並行序列 ＝ 每 GPU decode tok/s ÷ 每用戶 tok/s**。在模型裡，每步時間＝固定延遲＋批次 × 每序列時間，所以每用戶速度一旦固定，批次就由每序列時間決定。

|---|---|---|---|---|---|
| DeepSeek 線上服務（24 小時平均） | H800；V3／R1（671B／37B）；KV 平均 4,989 | 20–22 | 1,850 | **84–92** | Interested-party |
| DeepSeek profile | H800；EP128；4K | 約 18（2,324 ÷ 128） | 2,324 | **128**（官方寫明） | Interested-party |

| vLLM GLM-5.2-NVFP4 | 8×B300 decode＋16 prefill；744B／40B；MTP 3；16K／1K | 約 50（平均 TPOT ≤ 20 ms） | 未寫 | **≤ 37**（並行 300 ÷ 8，上限） | Interested-party |

讀法：
- 速度與批次的關係有兩個獨立方向證據：CloudMatrix 由 20 提高到 67 tok/s，吞吐降約 3.6 倍；Perplexity 單機在 40–80 tok/s 區間急降。OpenAI 的 30–65 tok/s 落在這個「批次明顯變小」的區段。
- **GB300 小批次一致**：vLLM GLM-5.2（40B 啟用、16K、MTP，與 Sol 很接近）在約 50 tok/s 時每顆 decode GPU 至多約 37 序列；模型 GB300 Sol 在 50 tok/s 時為 34.5（比值約 0.93）。這與 V12（0.99）同方向：擬合世代在擬合範圍內是對的。
- **Hopper 偏差在小批次也存在（只有類比證據）**：CloudMatrix 在 67 tok/s 仍有每 NPU 約 8 序列；模型 Hopper Sol 在 65 tok/s 只有 2.1。Hopper 小批次的非 SemiAnalysis 證據：已搜尋，未找到（InferenceX H200 只作旁證）。

註（Derived，粗估）：「模型同條件值」用診斷報告第 2.2 節 Calib 路線的 V3 架構結果反推：Hopper 每序列約 1.05 ms，由 C1（ITL 100 ms 時 744 tok/s，批次 74.4）得固定延遲約 21.9 ms。在每用戶 20 tok/s、無 MTP 時，每步 50 ms，批次約 26.8，decode 約 535 tok/s/GPU。要達到 DeepSeek 的 1,850–2,324，每序列時間要縮小約 **3.6–4.3 倍**。這與診斷報告用 LMSYS 得到的 3.7–4.2 倍一致，所以 V7 的 Hopper 偏差得到一個**非 LMSYS 的獨立確認**。

觀察：
1. **Hopper**：兩個 DeepSeek 點都顯示模型偏低約 4 倍，與 LMSYS 一致。
2. **GB200**：有明確 SLO 的大批次點（MLPerf server）只偏低 1.4 倍；沒有 SLO 的點（vLLM 10.1K、LMSYS 13,386）偏低 2.6–3.7 倍。LMSYS 的大差距有一部分來自「無 SLO、只算 decode GPU、NVFP4」這些寬鬆條件。
3. **批次相依性**：在 MLPerf v6.0 同一來源中，GB200 的模型比值在小批次（interactive 0.49）比大批次（server 0.72）更低；GB300 兩者相近（interactive V4 0.70、server 72 GPU 機櫃 5,030 ÷ 5,562–7,994 ＝ 0.63–0.90）。所以**沒有證據顯示偏差隨批次放大**；偏差比較像依世代而定（GB300 接近、GB200 偏低約 1.4–2 倍、Hopper 偏低約 4 倍）。
4. 附帶發現：工作簿 V3 的 8,064 是 Nebius **8 GPU 單機**的結果；同輪 72 GPU 機櫃為 NVIDIA 5,562、Nebius 7,994。V3 用的不是機櫃規模，請 Project 判斷是否改用 72 GPU 值。

## 5. 要成立什麼

情境計算頁用 v10.0 Perf 現值，以模型自己的 decode 公式改每用戶速度 S 與每序列時間縮小倍數 k，粗估每 GW 產出（IF_TokGW）的變化；再以層級 token 權重（0.4／0.45／0.15）與 2025 服務世代組合（Hopper 0.6／GB200 0.4）加權，假設機隊付費 token 與 IF_TokGW 成正比，得 L1_MFleet 粗估（現值 0.550）。這些是 Derived 粗估，不是建議值。

| 情境 | 條件 | IF_TokGW 變化（各格） | 2025 機隊 token | L1_MFleet 粗估 |
|---|---|---|---|---|
| A1 小批次成立、SLO 改觀測中位 | S＝90／55／40，k＝1 | Hopper ×1.24–1.93；GB200 ×1.09–1.37；GB300 ×1.09–1.53 | ×1.30 | 0.55 → **0.42** |
| A2 小批次成立、用 ChatGPT 舊預設 | S＝60／30／30，k＝1 | Hopper ×1.69–2.45；GB200 ×1.29–1.60 | ×1.57 | → 0.35 |
| A3 A1＋世代換算修正 | A1，k：Hopper 3.6、GB200 1.4、GB300 1 | Hopper ×2.8–4.7；GB200 ×1.45–1.84；GB300 同 A1 | ×1.99 | → 0.28 |
| B1 大批次、η_d 不變 | S＝20，k＝1 | Hopper ×1.9–2.9；GB200 ×1.40–1.83 | ×1.76 | → 0.31 |
| B2 大批次、η_d 隨批次（低） | S＝20，k：Hopper 3.6、Blackwell 1.4 | Hopper ×3.6–6.1；GB200 ×1.8–2.4 | ×2.56 | → 0.22 |
| B3 大批次、η_d 隨批次（高） | S＝20，k：Hopper 4.3、Blackwell 2.7 | Hopper ×3.8–6.5；GB200 ×2.9–3.8 | ×3.66 | → 0.15 |

### 若主力 token 在小批次、高互動下服務（證據較支持這一邊）

- 支持的證據：OpenAI 標準端點 30–127 tok/s、ChatGPT／Codex 預設 30→50 tok/s，都遠高於 DeepSeek 的 20 與 MLPerf server 的 12.5；GB300 在 50 tok/s 的小批次點與模型一致（vLLM GLM-5.2、V12）。
- **η_d 不必隨批次變化。** V7、V8 的判準應改為條件對齊後比較（另開「LMSYS 條件欄」，比照 Calib H 節）。
- 但即使如此，SLO 本身偏嚴：改成觀測中位，IF_TokGW 增加約 10%–90%（Astra、Hopper 增加最多），機隊 token 約 ×1.3，L1_MFleet 由 0.55 降到約 0.42。
- 另一個獨立問題仍在：Hopper 在大批次的非 LMSYS 點（DeepSeek）偏低約 4 倍，GB200 在 MLPerf 小批次也偏低約 2 倍。這指向世代換算（Hopper η_d 倍數 1.2 與每層延遲倍數 1.5、GB200 與 GB300 共用 η_d 0.0358），不是批次。若照 A3 修正，機隊 token 約 ×2，L1_MFleet 約 0.28。

### 若主力 token 實際在大批次下服務

- 需要的證據（本段沒找到）：OpenAI 主力 token 大部分走 Flex、Batch 或每用戶 20 tok/s 左右的路徑。現有的唯一跡象是 ChatGPT／Codex 在 2026-10-05 前預設約 30 tok/s。
- η_d 就需要隨批次變化。校準點建議：Hopper 用 DeepSeek profile（2,324，批次 128，4K），Blackwell 用 vLLM GB200（10.1K，批次填滿 HBM）；驗證點用 DeepSeek 線上服務、MLPerf v6.0 server，以及現有的 V7、V8。
- 影響：機隊 token 約 ×1.8（η_d 不變，只放寬速度）到 ×2.6–3.7（η_d 隨批次），L1_MFleet 約 0.31 → 0.15–0.22。
