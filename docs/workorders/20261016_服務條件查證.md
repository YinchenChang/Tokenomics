## 背景

- 診斷結論：η_d 只用 GB300 的兩個小批次點（每 GPU 3 與 19 個序列）擬合，之後對所有批次固定不變；因此在大批次下偏低約 4 倍。
- 但模型 Sol 的服務條件是每用戶 65 tok/s，加上 MTP，每顆 Hopper 只放約 2 個序列，落在擬合範圍內。
- 所以真正承重的問題是：**主力 token 實際是在什麼互動速度與批次下服務的。**

## 題目

### Q1 主力模型實際的每用戶輸出速度
- 對象：2025–2026 年 OpenAI 主力模型（Luna、Sol、Astra 三個層級的代表模型，層級對應依 2Q 第 1.2 節）。
- 要找：API 與 ChatGPT 的每用戶輸出速度（tok/s）、首 token 時間。
- 第三方量測：例如 Artificial Analysis 的 output speed／latency、OpenRouter 的吞吐量統計。
- 第二來源：使用者量測或論文。
- 輸出：每個層級的中位數與區間，並與模型的 SLO（Serving 頁 TPOT、TTFT；Sol 為每用戶 65 tok/s）比較。

### Q2 生產環境的批次與並行度
- 要找：公開的大規模服務批次規模、每 GPU 並行序列數。
  - 例如 DeepSeek 公開的生產數據（H800，24 小時平均）。
  - vLLM、SGLang 生產部署案例。
  - 雲端業者的說明。
- 輸出：每 GPU 並行序列的範圍，並與模型「每 GPU 約 2 個序列（Hopper Sol）」比較。
- 同時整理：互動速度與批次之間的換算關係，要有來源。

### Q3 大批次 decode 效率的獨立點（不可用 LMSYS）
- 目的：若日後要讓 η_d 隨批次變化，需要校準點，而且不能用 LMSYS（它是 V7、V8 的驗證點）。
- 要找：與 LMSYS 不同來源的大批次 decode 實測，例如：
  - vLLM H200（CoreWeave）約 2,200 tok/s/GPU；
  - DeepSeek 生產 decode 約 1,850；
  - 其他論文。
- 每點須寫明：硬體、模型、批次、ITL 或 TPOT。
- 每點標明可作「校準」或「驗證」，兩者不得重用同一點。

### Q4 V2 的替代上限
