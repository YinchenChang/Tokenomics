## 一句話結論

**2.15 倍的落差與價格時間錯配無關（兩個 m 共用同一個單價，比值不受影響，解釋力 0%）；模型原本拿來解釋它的「輸入長度口徑差 2.31」改用實際的輸入輸出比與快取重算後約為 1.0（0.65–1.2），也解釋不了；計價倍數與利用率的新證據都把機隊估得更大而不是更小；唯一能縮小機隊端的是「推論支出」到底取 Azure 帳單 12.6B 還是 OpenAI 自己的帳 8.4B（單獨可縮小約 53%）；需求端則要每則 token 落在區間上緣（約 11,000）才縮得動（可縮小至約 78%）。所以基準值下沒有任何單一項目能閉合，閉合要靠「機隊端支出口徑偏高」加「需求端長尾偏低」兩者並存。**

## 結論（先讀這段）

1. **缺口是一個恆等式，不是四個獨立因素的乘積。** 兩個 m 的分子與單價相同，所以 2.152（＝機隊 token ÷ 需求 token）恆等於：`L1_ScaleServe` 7.378 ÷（計價倍數 2.0 × 利用率比 IF_Util÷實際＝0.6÷0.35＝1.714）。把 7.378 分到三項去解釋，剩下要由「機隊容量被高估」或「需求被低估」來吸收的正好是 2.15。
2. **四項口徑差的乘積 13.4 > 7.378，主因是「每則提示 2.0」被重複計入。** `L1_ScaleServe` 的分母（token 路線服務 GW）已經用 4,000 tok 算；API 部分不隨每則 token 變，所以 4,000 對 2,000 的有效倍數只有 **1.30**，不是 2.0。換成 1.30，乘積為 8.74，對照 v5.28 基準（2,000 tok）下的 ScaleServe 9.60，解釋力 91%——這是 v5.29 當時的真實對照，不是 7.378。
3. **「輸入長度口徑差」GapISL 2.31 不能當作機隊端高估的證據。** 它來自 Sens_Perf 的「ISL 4K、輸出仍固定 2K」一欄；那欄的輸出占比（33%）遠高於實際流量。實際流量的輸入：輸出約 8–15：1（OpenRouter 6,000：400；另一個無關的無伺服器平台一年 6.1 十億請求，輸入 35.8T：輸出 2.5T＝14：1；DeepSeek 2025-02 為 3.6：1），而且快取命中很高。用 Sens_Perf 的每 token GPU 秒數線性重算（第 3.2 節，已驗證可重現 2.307），ChatGPT 型請求容量約為參考請求的 0.7–0.8 倍，API 型約 1.5–2.2 倍，按 GW 加權後 **κ≈1.0（0.65–1.2）**。所以這一項的實際貢獻接近 0，不是 2.31。
4. **計價倍數（Azure 價 ÷ 持有成本）的證據指向 1.2–2.0，不是 2.0–3.0。** 純 GPU 租賃的實際毛利：Oracle 14%（→1.16 倍）、CoreWeave 調整後營業利益率 5%（→1.05 倍）、Oracle 對 OpenAI 的 $300B／5 年合約換算每 GW 年約 12–13.3 B（→對持有成本 0.98–1.51 倍）、H100 市集牌價（→1.3–1.5 倍）。只有 neocloud 的 H100 牌價（2.2 倍）與超大雲牌價（4–6 倍）高於 2.0，而那是牌價，不是 OpenAI 的長約價。**把倍數從 2.0 降到證據中心 1.5，機隊 token 變大 33%，缺口從 2.15 擴大到 2.87**，是方向相反的修正。
5. **利用率沒有可用的實測。** 已搜尋，未找到任何 OpenAI／Anthropic／Google 的「token 吞吐 ÷ 容量」實測。唯一可引用的是 DeepSeek 自揭的節點占用：日均 226.75 節點、尖峰 278（比值 0.82），而且夜間把節點讓給研究。這只能當上界參考；實際利用率 0.30–0.40 沒有被推翻也沒有被支持。
6. **價格時間錯配（A6）：對缺口 0%，對 m 水準約 −14% 至 −18%。** 以 2025 全年 OpenAI 中階牌價（GPT-4o→GPT-5→5.2）對 2026-09 Sol 快照，參考請求單價比 P_2025÷P_快照＝**1.17（0.83–1.36）**；中階＋低階各半為 **1.22（0.82–1.47）**。m_fleet 0.810 → 0.695／0.663；m_整體 1.743 → 1.50／1.43。2025 各模型的實際用量占比：已搜尋，未找到。實收單價（美元）本身不受影響，回本檢查也不受影響。
7. **回本檢查（先看敏感度）：** 要讓 m_fleet×L 低於 0.2952（＝回本線，等價於 L1_LReqFleet）才翻轉。現值下 L 低於 0.365 就翻轉（L 低端 0.342 已在其下）；m_fleet 低於 0.459（L＝0.643 時）才翻轉，需要計價倍數 ≤1.13、或實際利用率 ≥0.62；**在 L＝0.343 的低端，m_fleet 要 ≥0.863，現值 0.810 差 6%，不滿足；需求路線 m（1.74）滿足。** 結論取決於「真值落在機隊端還是需求端」，這正是閉合要回答的事。
8. **新揭露（2026-10-12 之後）：OpenAI 與 Anthropic 都沒有。** 已搜尋，未找到（不等於不存在）。補充的相關揭露都在 10-12 之前：Google 每月處理 3.2 千兆 token（2026-05-19，一手）；Microsoft「年化 1 兆 token 的客戶數 4 倍」（FY26 Q4）；OpenRouter 2026-10-08 週報（代理型流量快取約 87–90%）；OpenAI 內部 Codex 占輸出 token 99.8%（2026-06）。

## 4. 為什麼結論是「無單一主因」

- **需求端**：基準值（4,300／4,000）與 v5.33A 相符；只有取到區間上緣（11,000）才把缺口縮到 1.19，且代價是免費 token 同步放大（r 變大）。13,950 超出所有證據。
- **機隊端**：計價倍數與利用率的新證據讓機隊變大；請求形狀修正 κ≈1 不貢獻；唯一能把機隊拉下來的是「推論支出」基準：12.6B（洩漏的 Microsoft 文件，Microsoft 稱不準，且可能含抵用金）對 8.4B（OpenAI 自身帳目，與 70% 計算毛利吻合）。**營收 13.07B、免費推論 3.9B、訓練 12B、推論 8.4B 同屬 `SRC_DEM_004～007` 一組；機隊路線卻用另一組的 12.6B，等於兩組來源混用。**
- **價格口徑**：只改 m 的水準（−14～−18%），不改缺口、不改實收單價、不改回本。
